# DESIGN — +1

## 0. 문서 목적

이 문서는 `+1` MVP의 판매자/운영자 UI/UX 기준을 정의한다.

핵심 목표:

> 판매자는 실제 서비스를 통해 보관상품을 판매 등록한다고 느끼고, 운영자는 최소한의 화면으로 신청·모집·실험 현황을 관리한다.

---

# 1. 디자인 방향

서비스명:

```text
+1
```

디자인 톤:

> 편의점 앱처럼 친숙하고 가볍지만 실제 판매 신청을 처리하는 정식 서비스

참고 요소:

- 밝은 시안/민트 포인트
- 짙은 네이비 텍스트
- 둥근 카드와 버튼
- 짧고 직접적인 카피
- 모바일 앱 같은 사용감

사용하지 않는 요소:

- GS25/CU 공식 로고/캐릭터
- 공식 앱 화면 복제
- 공식 제휴로 오해할 표현
- 과도한 Dashboard 스타일

# 4. 판매자 공통 레이아웃

5단계 등록 화면은 동일한 기본 구조를 사용한다.

```text
┌───────────────────────────┐
│ ←        +1          2 / 5 │
│ ━━━━━━━━━━━━━○━━━━━━       │
│                           │
│ 화면 제목                  │
│ 짧은 설명                  │
│                           │
│ 현재 단계 내용             │
│                           │
├───────────────────────────┤
│        다음으로             │
└───────────────────────────┘
```

모바일:

- 단일 Column
- Primary CTA 하단 고정
- 터치 영역 최소 약 44px
- CTA 높이 52~56px

데스크탑:

- 판매 폼 최대 폭 약 560px
- CTA는 본문 아래 자연스럽게 배치

# 5. 판매자 홈

## open

Hero:

> 남은 +1 상품, 판매해보세요

서브 카피:

> GS25·CU 앱에 남아 있는 1+1 / 2+1 보관상품을 등록해주세요.

Primary CTA:

```text
판매 등록 시작
```

## paused

등록 CTA 대신 또는 비활성 상태와 함께 다음 안내를 보여준다.

> 판매 신청을 잠시 쉬고 있어요

> 현재 새로운 판매 신청을 받고 있지 않습니다.

## closed

> 현재 모집이 마감됐어요

> 판매 신청 모집이 종료되었습니다.

모집 상태를 불러오지 못하면 신청을 허용하는 CTA를 보여주지 않는다.

# 6. /sell 접근 상태

## paused

```text
판매 신청을 잠시 쉬고 있어요

[ 홈으로 ]
```

## closed

Form 미노출.

```text
현재 모집이 마감됐어요

[ 홈으로 ]
```

```text
현재 판매 신청 가능 여부를 확인하지 못했어요.

[ 홈으로 ]
```

# 7. 1단계 — 판매 조건

제목:

> 어떤 상품을 판매하시나요?

편의점:

```text
[ GS25 ] [ CU ]
```

행사:

```text
[ 1+1 ] [ 2+1 ]
```

안내:

> 한 번의 판매 신청에는 같은 편의점·같은 행사 상품만 등록할 수 있어요.

CTA:

```text
상품 등록하기
```

---

# 8. 2단계 — 상품 등록

제목:

> 판매할 상품을 등록해주세요

상품 카드:

```text
상품 1

상품명
[                         ]

유효기간 (선택)
[                         ]

행사 당시 가격
[                     원 ]

판매 희망 가격
[                     원 ]
```

상품 추가:

```text
＋ 상품 하나 더 등록하기
```

상품이 2개 이상일 때 추가된 상품은 삭제 가능.

최소 1개 유지.

가격 0원 입력 UI는 허용하지 않는다.

---

# 9. 3단계 — 보관상품 확인

제목:

> 보관 중인 상품을 확인할게요

설명:

> 편의점 앱에서 판매할 상품이 보이는 화면을 캡처해서 올려주세요.

스크린샷 1장:

- 업로드
- 미리보기
- 교체

OCR/QR 자동 판독 기능은 제공하지 않는다.

---

# 10. 4단계 — 연락처

제목:

> 어떻게 연락드리면 될까요?

연락 방식:

```text
[ 휴대폰 ] [ 카카오톡 ]
```

둘 중 하나만 선택.

개인정보 안내는 짧게 유지한다.

---

# 11. 5단계 — 신청 확인

제목:

> 판매 신청 내용을 확인해주세요

표시:

- 편의점 / 행사 유형
- 상품 목록
- 유효기간
- 행사 당시 가격
- 판매 희망 가격
- 증빙 이미지 Thumbnail
- 연락 방법 / 연락처

최종 CTA:

```text
판매 신청하기
```

제출 중:

```text
신청 중...
```

중복 클릭 불가.

---

# 12. 신청 완료

제목:

> 판매 신청이 접수됐어요

추가 행동을 강요하지 않는다.

Secondary Action:

```text
홈으로
```

# 13. Admin 공통 구조

Admin은 데스크탑 공간을 적극 활용해도 되지만 시각 언어는 +1을 유지한다.

Header 예:

```text
+1 Admin

[ 판매 신청 ] [ 모집 관리 ] [ 실험 현황 ]
```

Sidebar는 만들지 않는다.

현재 route는 selected state로 명확히 표시한다.

모바일 Admin은 기능 확인이 가능하도록만 대응하고, 주 사용 환경은 데스크탑을 우선한다.

---

# 14. Admin — 신청 목록

Route:

```text
/admin
```

상태 필터:

```text
전체 / 접수됨 / 연락중 / 처리완료
```

신청 정보:

- 신청 시점
- GS25/CU
- 1+1/2+1
- 상품 개수
- 연락 방식
- 상태

검색/날짜 필터는 추가하지 않는다.

---

# 15. Admin — 신청 상세

Route:

```text
/admin/:saleRequestId
```

섹션:

1. 신청 정보
2. 판매자 연락처
3. 판매 증빙 이미지
4. StoredItem 목록

received 상태:

```text
판매자에게 연락 시작
```

StoredItem pending 상태:

```text
[ 구매 ] [ 거절 ]
```

구매:

- 구매 증빙 이미지 필수
- 완료 후 readonly

거절:

- 거절 이유 필수
- 완료 후 readonly

모든 상품 처리 후:

> 모든 상품 처리가 완료되었습니다.

별도 완료 버튼은 만들지 않는다.

# 16. Admin — 모집 관리

Route:

```text
/admin/recruitment
```

페이지 제목:

```text
모집 관리
```

설명:

> 판매자 신청 접수를 제어합니다. 상태를 변경하면 즉시 판매자 화면에 반영됩니다.

## 카드 1 — 현재 상태

포함:

- 제목 `현재 상태`
- 상태 Badge
- 상태별 설명

UI Label:

```text
open   → 모집 중
paused → 일시중지
closed → 마감
```

## 카드 2 — 상태 변경

제목:

```text
상태 변경
```

설명:

> 한 번에 하나의 상태만 활성화할 수 있습니다. 변경 사항은 저장 즉시 적용됩니다.

선택:

```text
[ 모집 중 ] [ 일시중지 ] [ 마감 ]
```

현재 상태와 선택 상태가 같으면 저장 CTA 비활성.

Primary CTA:

```text
변경 사항 저장
```

저장 중:

```text
저장 중...
```

open → paused/closed 전환 시 기존 Confirmation Dialog 패턴을 재사용할 수 있다.

새로운 별도 Confirmation 시스템은 만들지 않는다.

# 17. Admin — 실험 현황

Route:

```text
/admin/experiment
```

이 화면은 사용자가 제공한 레퍼런스처럼 **밝은 배경 + 요약 카드 + 분석 카드** 구조를 사용한다.

일반 BI Dashboard처럼 복잡하게 만들지 않는다.

## Header

제목:

```text
실험 현황
```

하단:

```text
현재 모집 상태: [ 모집 중 ]
```

상태 Badge는 모집 관리와 동일한 component를 재사용한다.

## Summary Cards

데스크탑에서는 4개를 한 줄에 배치할 수 있다.

```text
[ 전체 판매 신청 수 ]
[ 고유 판매자 수   ]
[ 실제 구매 상품 수 ]
[ 처리 완료 신청 수 ]
```

값은 큰 숫자, Label은 작게 표시한다.

가짜 단위/증가율은 표시하지 않는다.

## Analysis Cards

### 판매 희망금액 분포

`asking_price`와 개수를 단순 표/목록으로 표시한다.

### 희망가격 비율 분포 — 분석용

```text
25% 이하
26~50%
51~75%
76~100%
100% 초과
```

표 또는 단순 CSS bar 정도만 허용한다.

Chart library는 추가하지 않는다.

### 편의점별 신청 수

```text
편의점 | 신청 수
```

### 행사 유형별 신청 수

```text
행사 유형 | 신청 수
```

### 상태별 신청 수

```text
상태 | 신청 수
```

### 상품 결과별 수

```text
결과 | 상품 수
```

### 재신청 판매자 수

숫자 또는 짧은 카드로 표시한다.

## Empty State

집계가 비어 있으면:

```text
데이터가 없어요.
```

데이터가 없을 때 fake chart/grid를 채우지 않는다.

# 20. 오류/로딩 UX

판매자:

- 입력 오류 → 필드 아래
- 업로드 실패 → 현재 단계 유지
- 상태 조회 실패 → 신청 CTA 숨김/차단
- 제출 실패 → 완료 화면 이동 금지

Admin:

- API 실패 → 현재 데이터 유지
- 저장 실패 → 성공 상태처럼 보이지 않음
- 실험 지표 실패 → 오류 상태 표시
- Loading skeleton 또는 단순 로딩 문구 허용

Supabase 원본 오류 문구를 그대로 사용자에게 노출하지 않는다.
