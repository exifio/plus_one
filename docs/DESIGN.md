# DESIGN — +1

## 0. 문서 목적

이 문서는 편의점 앱에 남아 있는 1+1 / 2+1 보관상품을 실제로 판매하려는 사람이 존재하는지 검증하기 위한 MVP 서비스 `+1`의 UI/UX 설계 기준을 정의한다.

이 문서는 확정된 PRD를 기준으로 하며, 기존 프로젝트의 디자인을 재사용하지 않는다.

핵심 목표는 다음과 같다.

> 사용자가 설문에 응답한다는 느낌이 아니라 실제 서비스를 통해 보관상품을 판매 등록한다고 느끼도록 한다.

---

# 1. 디자인 목표

`+1`은 편의점 앱에 남은 1+1 / 2+1 보관상품을 실제로 판매하려는 사용자가 복잡함 없이 판매 신청을 완료하도록 돕는 모바일 퍼스트 서비스다.

사용자가 받아야 할 인상은 다음과 같다.

> 편의점 앱처럼 친숙하고 가볍지만, 실제 판매 신청을 하는 정식 서비스

따라서 설문 서비스처럼 보이는 표현은 사용하지 않는다.

사용하지 않는 표현:

- 응답 제출
- 설문 시작
- 답변해주세요

사용하는 표현:

- 판매 등록 시작
- 상품 등록
- 판매 신청하기

---

# 2. 브랜드 방향

## 서비스명

`+1`

별도의 긴 서비스명을 사용하지 않고 `+1` 워드마크 자체를 브랜드의 중심으로 사용한다.

## 디자인 톤

전체적인 방향은 다음과 같다.

> 편의점 앱처럼 친숙한 생활형 서비스

GS25의 밝고 경쾌한 생활형 서비스 분위기를 참고하되, GS25 공식 서비스처럼 보이게 복제하지 않는다.

참고하는 요소:

- 밝은 시안/민트 계열 포인트
- 짙은 네이비 텍스트
- 둥근 카드와 버튼
- 명확한 정보 위계
- 친근하고 짧은 문장
- 모바일 앱 같은 사용감

사용하지 않는 요소:

- GS25 공식 로고
- GS25 공식 캐릭터
- GS25 앱 화면 직접 복제
- GS25 고유 그래픽 자산
- GS25 공식 서비스로 오해할 수 있는 표현

GS25와 CU 모두 지원하므로 전체 서비스 브랜드는 `+1`로 통일한다.

# 3. 디자인 원칙

## 3.1 모바일 퍼스트

판매자는 편의점 앱의 보관상품을 확인하면서 서비스를 이용할 가능성이 높으므로 모바일 경험을 최우선으로 설계한다.

## 3.2 실제 판매 서비스처럼 보이게 한다

입력 과정은 설문이 아니라 판매 등록 과정처럼 느껴져야 한다.

## 3.3 한 화면에는 하나의 주요 목적만 둔다

현재 단계에서 필요한 정보만 보여준다.

## 3.4 등록 단계를 불필요하게 늘리지 않는다

판매 등록은 5단계로 유지한다.

## 3.5 핵심 행동을 항상 명확하게 한다

각 화면에서 사용자가 다음에 해야 할 행동을 바로 이해할 수 있어야 한다.

## 3.6 기능을 추가해 화면을 채우지 않는다

홈이나 빈 화면이 심심해 보여도 검증과 관계없는 기능을 추가하지 않는다.

8. 신청 목록
9. 신청 상세

# 5. 판매 등록 플로우

```text
홈
↓
1. 판매 조건
↓
2. 상품 등록
↓
3. 보관상품 확인
↓
4. 연락처
↓
5. 신청 확인
↓
신청 완료
```

한 SaleRequest 안에서 편의점과 행사 유형은 하나로 고정한다.

예:

```text
GS25
1+1

상품 A
상품 B
상품 C
```

가능.

다음은 불가능하다.

```text
GS25 상품 + CU 상품
```

또는

```text
1+1 상품 + 2+1 상품
```

다른 편의점이나 다른 행사 유형을 판매하려면 별도 판매 신청을 생성한다.

# 6. 공통 판매 등록 레이아웃

5개의 판매 등록 화면은 동일한 기본 구조를 사용한다.

```text
┌───────────────────────────┐
│ ←        +1          2 / 5 │
│ ━━━━━━━━━━━━━○━━━━━━       │
│                           │
│ 화면 제목                  │
│ 짧은 설명                  │
│                           │
│       현재 단계 내용        │
│                           │
│                           │
├───────────────────────────┤
│        다음으로             │
└───────────────────────────┘
```

## 상단

- 뒤로가기
- `+1` 워드마크
- 현재 단계 `n / 5`
- 간단한 진행률

## 본문

현재 단계에서 필요한 내용만 표시한다.

## 하단

모바일에서는 Primary CTA를 하단에 고정한다.

이전 단계 이동은 상단 뒤로가기를 사용한다.

키보드가 올라왔을 때 CTA가 입력 필드를 가리지 않도록 한다.

데스크탑에서는 CTA를 본문 아래에 자연스럽게 배치한다.

# 7. 화면 01 — 홈

## 목적

사용자가 서비스 목적을 짧은 시간 안에 이해하고 판매 등록을 시작하도록 한다.

긴 사업 설명이나 검증 목적은 노출하지 않는다.

## Header

`+1`

별도 메뉴는 두지 않는다.

## Hero

메인 카피:

> 남은 +1 상품,  
> 판매해보세요

서브 카피:

> GS25·CU 앱에 남아 있는  
> 1+1 / 2+1 보관상품을 등록해주세요.

Primary CTA:

`판매 등록 시작`

## 비주얼

다음과 같은 자체 그래픽을 사용할 수 있다.

- 둥근 청록색 영역
- `+1` 기호
- 상품 카드 형태의 추상 그래픽
- 스마트폰과 보관상품을 연상시키는 간단한 mock UI

실제 GS25/CU 앱 화면이나 공식 캐릭터는 사용하지 않는다.

## 간단한 이용 안내

```text
1
판매할 상품을 등록해요

2
보관 중인 화면을 올려요

3
확인 후 연락드려요
```

실제 등록은 5단계지만 홈에서는 사용자의 체감 흐름만 간단히 표현한다.

## 지원 대상 안내

```text
현재 GS25 · CU
1+1 · 2+1 상품을 등록할 수 있어요.
```

# 8. 화면 02 — 1단계 판매 조건

## 제목

> 어떤 상품을 판매하시나요?

설명:

> 편의점과 행사 종류를 먼저 선택해주세요.

## 편의점 선택

`보관 중인 편의점`

```text
[ GS25 ]    [ CU ]
```

하나만 선택할 수 있다.

## 행사 유형 선택

Label:

`행사 종류`

선택 카드:

```text
[ 1+1 ]    [ 2+1 ]
```

하나만 선택할 수 있다.

## 안내

> 한 번의 판매 신청에는 같은 편의점·같은 행사 상품만 등록할 수 있어요.

두 값이 모두 선택되기 전:

`상품 등록하기` 비활성

두 값이 모두 선택된 후:

`상품 등록하기` 활성

# 9. 화면 03 — 2단계 상품 등록

이번 MVP에서 가장 중요한 입력 화면이다.

## 제목

> 판매할 상품을 등록해주세요

설명:

> 보관상품 1개당 하나씩 입력해주세요.

## 상품 카드

첫 번째 상품은 기본으로 존재한다.

각 상품은 하나의 카드로 표현한다.

```text
상품 1

상품명
[ 상품명을 입력해주세요             ]

유효기간
[ 날짜 선택                         ]

행사 당시 가격
[                              원   ]

판매 희망 가격
[                              원   ]
```

### 상품명

텍스트 입력.

예시 Placeholder:

`코카콜라 제로 500ml`

상품 검색, 자동완성, 상품 마스터는 사용하지 않는다.

### 유효기간

날짜 선택 UI를 사용한다.

- 지난 날짜 선택 불가
- 오늘 날짜 선택 가능

### 행사 당시 가격

숫자 키패드를 사용한다.

표시 예:

`2,200원`

### 판매 희망 가격

숫자 키패드를 사용한다.

설명:

> 실제로 판매하고 싶은 가격을 입력해주세요.

추천 가격이나 할인율을 보여주지 않는다.

## 상품 추가

첫 상품 아래에 다음 Secondary Action을 둔다.

`＋ 상품 하나 더 등록하기`

추가 시 동일 화면에 새 카드가 생성된다.

```text
상품 1
...

상품 2
...

＋ 상품 하나 더 등록하기
```

## 상품 삭제

상품이 2개 이상일 때 추가된 상품은 삭제할 수 있다.

최소 1개는 반드시 존재해야 한다.

이는 제출 전 입력 편집 기능이며 판매 신청 취소 기능과는 다르다.

## CTA

`보관상품 확인하기`

모든 상품 필수값이 유효할 때 활성화한다.

- 다른 이미지 선택

## CTA

이미지 미등록:

`연락처 입력하기` 비활성

# 12. 화면 06 — 5단계 신청 확인

사용자가 입력한 데이터를 폼 형태가 아니라 실제 판매 신청 내역처럼 보여준다.

## 제목

> 판매 신청 내용을 확인해주세요

설명:

> 마지막으로 입력한 내용을 확인해주세요.

## 신청 조건

예:

```text
GS25 · 1+1
```

필요한 경우 `변경`으로 해당 단계로 돌아간다.

별도 수정 화면은 만들지 않는다.

## 상품 영역

상단:

`판매 상품 2개`

각 상품은 요약 카드로 표시한다.

```text
행사 당시 가격
2,200원

1,000원
```

가장 강조할 값은 `판매 희망 가격`이다.

## 보관상품 이미지

업로드한 이미지 Thumbnail을 보여준다.

`변경`으로 3단계로 돌아갈 수 있다.

## 연락 정보

```text

휴대폰

연락처
010-1234-5678
```

## 최종 CTA

`판매 신청하기`

# 13. 화면 07 — 신청 완료

## 목적

판매 신청이 실제로 정상 접수되었다는 확신을 준다.

추가 행동을 강요하지 않는다.

## 메인

체크 그래픽.

> 판매 신청이 접수됐어요

설명:

> 등록해주신 상품을 확인한 뒤  
> 필요한 경우 입력하신 연락처로 연락드릴게요.

## 다음 과정 안내

```text
신청 접수
   ↓
상품 확인
   ↓
필요 시 연락
```

진행 상태 조회 기능처럼 보이지 않도록 간단한 설명만 제공한다.

## CTA

필수 CTA는 없다.

Secondary Action으로 `홈으로` 정도만 허용한다.

# 14. Admin 화면 방향

Admin은 운영자 한 명이 사용한다.

판매자 화면과 동일한 감성 강도를 적용할 필요는 없지만 `+1`의 컬러, 타이포, 카드 스타일은 공유한다.

운영 기능보다 관리 편의 기능을 과도하게 추가하지 않는다.

Admin 주요 화면은 다음 두 개다.

1. 신청 목록
2. 신청 상세

# 15. Admin 01 — 신청 목록

## Header

```text
+1 Admin

판매 신청
```

Sidebar는 만들지 않는다.

## 상태 필터

# 19. 구매 처리 UX

`구매`를 선택하면 즉시 확정하지 않는다.

Modal 또는 Bottom Sheet를 사용한다.

제목:

> 이 상품을 구매 처리할까요?

필수 입력:

`구매 증빙 이미지`

CTA:

`구매 처리`

구매 증빙 없이는 처리할 수 없다.

완료 후:

```text
✓ 구매
```

상태로 고정한다.

# 20. 거절 처리 UX

`거절` 선택 시 Modal 또는 Bottom Sheet를 사용한다.

제목:

> 거절 이유를 입력해주세요

입력:

```text
[ 거절 이유를 입력해주세요 ]
```

CTA:

`거절 처리`

거절 이유가 없으면 완료할 수 없다.

완료 후 `거절` 상태로 고정한다.

# 21. 처리 결과 불변성

구매 또는 거절 처리된 상품에는 다시 처리 버튼을 보여주지 않는다.

구매:

```text
✓ 구매 완료

구매 증빙
[ 이미지 ]
```

거절:

```text
거절

거절 이유
유효기간이 너무 짧음
```

다음 기능은 제공하지 않는다.

- 수정
- 되돌리기
- 상태 변경

이는 PRD의 상태 불변성 규칙을 UI에서도 그대로 반영한 것이다.

# 26. 모바일 UX 기준

- 좌우 여백 약 20px
- 터치 영역 최소 약 44px
- 본문 기본 16px
- Primary CTA 높이 52~56px

- 숫자 입력은 숫자 키패드
- 날짜 입력은 모바일 친화적 날짜 UI

# 39. 최종 사용자 경험

판매자는 다음 경험만 하면 된다.

> 남은 상품이 있다  
> → 판매 등록을 시작한다  
> → 실제 상품 정보를 입력한다  
> → 보관 사실을 보여준다  
> → 연락처를 남긴다  
> → 판매 가격을 확인한다  
> → 판매 신청한다

운영자는 다음 경험만 하면 된다.

> 신청을 확인한다  
> → 판매자에게 연락한다  
> → 상품별 구매/거절을 처리한다  
> → 실제 결과를 기록한다

이 두 흐름 외의 경험은 MVP에서 추가하지 않는다.
