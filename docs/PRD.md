# 판매자 공급 검증 MVP — PRD

## 1. 제품 정의
GS25/CU 1+1·2+1 행사로 받은 뒤 보관함에 남아 있는 상품을 **실제로 판매하려는 사람이 존재하는지 확인하기 위한 판매자 전용 웹서비스**다.

장기적으로는 보관상품 C2C 거래 서비스로 발전할 수 있지만, 현재 MVP의 최우선 질문은 하나다.

> 실제 보관상품을 가진 사람이 원하는 판매금액과 연락처를 남기며 판매 신청까지 하는가?

구매자 수요 검증은 이번 범위에 포함하지 않는다. 현재 운영자는 구매자 역할을 직접 수행한다.

판매자 화면은 실험·설문처럼 보이지 않고 실제 운영 서비스처럼 보여야 한다.

### 사용자에게 전달할 핵심 약속
정상적인 판매 신청은 운영자가 임의로 선별하지 않고 **직접 구매를 진행한다.**

사용자에게 `가능한 경우 구매`, `검토 후 매입 여부 결정`처럼 불확실하게 표현하지 않는다.

권장 표현:

> 판매 신청을 남겨주시면 제가 직접 구매할게요. 구매 진행을 위해 입력하신 연락처로 증빙과 QR 전달 방법을 안내드릴게요.

허위·중복 신청, 이미 사용된 상품, 연락 불가 등 정상적인 거래 자체가 불가능한 경우는 운영 예외로 처리한다.

## 2. 이번 MVP에서 확인할 것
우선순위는 다음과 같다.

1. 사용하지 않을 편의점 보관상품을 가진 사람이 실제 판매 신청까지 하는가
2. 판매자는 해당 상품을 얼마에 판매하고 싶어 하는가
3. 신청 이후 연락 → 증빙 확인 → QR 전달 → 실제 구매 완료까지 이어지는가

가격 협상 반응이나 최적 가격 탐색은 현재 핵심 가설이 아니다.

## 3. 이번 MVP에서 만들지 않는 것
- 구매자 기능 및 구매자 상품 목록
- 결제/PG 및 자동 정산
- 판매자 회원가입/로그인
- 채팅
- QR OCR 및 중복 QR 자동 탐지
- 이미지 OCR 및 자동 상품 판독
- 자동 상품 검색
- 0~100% 가격 선택 UI
- 10%p 낮은 가격 재제안
- 자동 가격 최적화
- 판매자 등급
- 네이티브 앱
- 불필요한 미래 확장 구조

## 4. 사용자
### 판매자
- 회원가입/로그인 없음
- 보관상품을 `스크린샷 등록` 또는 `직접 입력` 중 편한 방식으로 알려줌
- 판매 희망금액과 연락처를 남김
- 최초 신청 단계에서는 QR 자체를 제출하지 않음
- 신청 후 운영자 연락에 따라 증빙과 QR 전달을 진행함

### 관리자
- 모든 정상 신청을 구매 진행 대상으로 확인
- 판매자에게 연락
- 증빙 및 QR 확인
- 진행 상태 변경
- 모집 진행/일시중지/종료
- 판매 희망금액과 진행 현황 확인

실제 관리자 인증은 Backend Phase에서 구현하고 Frontend에서는 Mock으로 처리한다.

## 5. 판매자 흐름
전체 신청 흐름은 **3단계 + 완료 화면**으로 제한한다.

### 1단계 — 편의점 / 행사 유형
필수 선택:
- 편의점: `GS25 | CU`
- 행사 유형: `1+1 | 2+1`

단계명은 `상품 유형 선택`보다 **`편의점·행사 선택`**처럼 실제 행동을 명확히 표현한다.

### 2단계 — 상품 정보 등록
먼저 등록 방식을 선택한다.

#### 방식 A — 스크린샷으로 등록
판매자가 보관함에서 해당 상품을 확인할 수 있는 **스크린샷 1장**을 업로드한다.

- 추가 상품 정보 입력을 강제하지 않는다.
- 이미지에서 상품을 자동 판독하지 않는다.
- 현재는 한 신청에서 한 상품 판매를 전제로 한다.
- Frontend Mock 단계에서는 업로드 UI, 미리보기, 교체/삭제 정도만 구현한다.
- 실제 파일 저장 방식은 Backend Phase의 `docs/BACKEND.md`에서 결정한다.

#### 방식 B — 직접 입력으로 등록
직접 입력 항목:
- 상품명 — 필수
- 행사 당시 실제 결제금액 — 필수
- 소비기한/유효기간 — 선택

판매 희망 수량을 별도 입력받지 않는다. 현재 MVP는 **1개 판매 신청만 지원**하며 내부적으로 수량 `1`로 처리한다.

2단계 안내는 사용자가 선택한 방식에 필요한 정보만 보여준다. 두 방식의 입력 폼을 동시에 노출하지 않는다.

### 3단계 — 판매 희망금액 / 연락처
필수 입력:
- 판매 희망금액
- 연락 수단 종류
- 연락 정보

연락 수단 MVP:
- 휴대전화 번호
- 카카오톡 연락 정보(ID, 오픈채팅 링크 또는 연락 가능한 텍스트)

둘 중 하나의 유효한 연락 수단만 있으면 된다.

판매 희망금액은 사용자가 직접 원 단위 금액으로 입력한다. 가격 비율 선택이나 추가 할인 제안 단계는 없다.

CTA:

> 판매 신청하기

별도 최종 확인 페이지는 만들지 않는다.

### 신청 완료
제출 후 바로 완료 화면을 보여준다.

완료 화면의 핵심 안내:
- 판매 신청이 정상 접수됨
- 운영자가 직접 구매를 진행함
- 입력한 연락처로 증빙과 QR 전달 방법을 안내함
- 구매 진행 전 QR을 먼저 보내지 않도록 안내할 수 있음

권장 표현:

> 판매 신청이 완료되었습니다. 입력하신 연락처로 구매 진행 방법을 안내드릴게요.

긴 내부 UUID는 사용자에게 반드시 노출할 필요가 없다. 신청번호가 필요하면 짧고 읽기 쉬운 형태를 사용한다.

## 6. 가격 데이터 규칙
사용자에게는 **판매 희망금액만 직접 입력**하게 한다.

### 핵심 가격 데이터
- 모든 신청: 판매 희망금액
- 직접 입력 신청: 실제 결제금액을 이용해 참고용 가격 비율 계산 가능
- 스크린샷 신청: 실제 결제금액이 없을 수 있으므로 가격 비율 계산을 필수로 하지 않음

직접 입력 신청에 한해 내부적으로 다음을 계산할 수 있다.

#### 행사 기준 1개 가격
- 1+1: `실제 결제금액 ÷ 2`
- 2+1: `실제 결제금액 ÷ 3`
- 분석용 기준가격은 100원 단위 반올림 가능

`행사기준1개가격 = round100(실제결제금액 / 행사기준수량)`

#### 판매 희망가격 비율
`희망가격비율 = 판매희망금액 / 행사기준1개가격 × 100`

이 비율은 관리자 참고용이며 판매자에게 선택지로 제시하지 않는다.

현재 MVP의 핵심은 정교한 가격 비율 분석이 아니라 **판매 신청 존재 여부와 판매자가 직접 입력한 희망금액 분포**다.

## 7. 모집 상태
- `OPEN`: 신청 가능
- `PAUSED`: 일시중지 안내 후 신청 불가
- `CLOSED`: 모집 종료 안내 후 신청 불가

관리자가 상태를 변경한다.

## 8. 관리자 진행 상태
1. `SUBMITTED` — 신청됨
2. `CONTACTED` — 연락함
3. `EVIDENCE_VERIFIED` — 증빙 확인
4. `QR_RECEIVED` — QR 전달
5. `COMPLETED` — 구매 완료
6. `FAILED` — 진행 실패

정상 신청은 기본적으로 구매 대상으로 처리하므로 `NOT_PURCHASED`를 일반적인 선별 상태로 사용하지 않는다.

허위·중복·사용 완료 상품 등 거래 자체가 불가능한 예외가 발생하면 `FAILED`로 처리하고 필요한 경우 사유를 남긴다.

별도 상태 이력 시스템은 실제 필요가 생기기 전까지 만들지 않는다.

## 9. 관리자 Frontend
### 로그인
간단한 관리자 로그인 화면. 실제 Supabase Auth는 Backend Phase에서 구현한다.

### 신청 목록
최소 표시 정보:
- 신청일
- 편의점 / 행사 유형
- 등록 방식
- 상품명 또는 `스크린샷 등록`
- 판매 희망금액
- 현재 상태

### 신청 상세
공통:
- 편의점 / 행사 유형
- 등록 방식
- 판매 희망금액
- 연락 수단
- 현재 상태
- 상태 변경 UI

스크린샷 등록:
- 업로드한 이미지 확인

직접 입력:
- 상품명
- 실제 결제금액
- 소비기한/유효기간
- 필요 시 행사 기준 1개 가격 및 희망가격 비율

### 최소 현황
- 전체 신청 수
- 등록 방식별 신청 수
- 편의점별 신청 수
- 행사 유형별 신청 수
- 판매 희망금액 분포
- 상태별 신청 수
- 구매 완료 수

차트는 필수가 아니다. 숫자 카드, 표, 단순 목록으로 충분하다.

### 모집 관리
`OPEN / PAUSED / CLOSED`를 변경할 수 있다.

## 10. Backend가 보존해야 할 핵심 데이터
공통:
- 편의점
- 행사 유형
- 등록 방식: `SCREENSHOT | MANUAL`
- 판매 희망금액
- 연락 수단 종류 + 연락 정보
- 신청 상태
- 생성/수정 시각

스크린샷 등록:
- 이미지 참조 정보

직접 입력:
- 상품명
- 실제 결제금액
- 소비기한/유효기간

판매 수량은 현재 MVP에서 `1`로 고정한다.

이미지 저장, 접근 권한, 삭제 정책은 Frontend 승인 후 `docs/BACKEND.md`에서 결정한다.

## 11. 랜딩 핵심 안내
랜딩의 `어떻게 진행되나요?`는 실제 V2 흐름과 일치해야 한다.

1. **편의점·행사 선택**  
   GS25/CU와 1+1·2+1을 선택해요.

2. **상품 정보 등록**  
   스크린샷을 올리거나 직접 상품 정보를 입력해요.

3. **희망금액·연락처 입력**  
   받고 싶은 금액과 연락처를 남기면 제가 직접 구매를 진행할게요.

V1의 `가격 선택`, `가능한 경우 연락`, `매입 여부 확인 후 결정` 등의 문구를 남기지 않는다.

## 12. UX 원칙
- 판매자에게 `실험`, `MVP`, `가설` 같은 표현을 보여주지 않는다.
- 작은 범위라도 실제 서비스처럼 느껴지게 한다.
- 신청을 최대한 짧게 끝낼 수 있게 한다.
- 한 단계에서 핵심 행동을 하나만 강조한다.
- 불필요한 중간 완료/확인 화면을 만들지 않는다.
- 가격 협상을 유도하거나 특정 가격을 정답처럼 제시하지 않는다.
- 스크린샷 등록은 직접 입력보다 복잡하게 만들지 않는다.
- 구매 의사를 흐리는 조건부 표현을 사용하지 않는다.
- 가짜 긴급성, 가짜 거래 건수, 가짜 후기를 사용하지 않는다.

## 13. 기술 방향
Frontend는 React + Vite + TypeScript + Zod + Mock 데이터로 구성한다.

스크린샷 등록의 실제 파일 저장은 Frontend 승인 뒤 Backend Phase에서 Supabase Storage 사용 여부를 포함해 결정한다.

Backend는 승인된 Frontend를 기준으로 Supabase PostgreSQL/Auth를 붙이고 Vercel에 배포한다.

Frontend Phase에서는 별도 Backend framework를 추가하지 않는다.

## 14. Frontend 승인 조건
다음이 모두 만족되어야 Backend Preparation으로 넘어간다.
- 랜딩부터 신청 완료까지 3단계 판매자 흐름이 정상 동작
- 편의점/행사 유형 선택 가능
- 2단계에서 `스크린샷 등록 / 직접 입력` 중 하나 선택 가능
- 스크린샷 등록은 이미지 1장 선택·미리보기 가능
- 직접 입력은 상품명·실제 결제금액 입력 가능, 유효기간은 선택
- 판매 희망 수량 입력 UI 제거, 내부 수량 1로 처리
- 판매 희망금액과 연락처 입력 후 바로 신청 가능
- 0~100% 가격 선택, 10%p 재제안, 별도 최종 확인 페이지 없음
- 랜딩·3단계·완료 화면에서 `가능한 경우 구매`류 문구 제거
- 신청 완료 후 직접 구매 진행과 후속 연락을 명확히 안내
- 관리자 Mock에서 두 등록 방식 모두 구분하고 확인 가능
- OPEN/PAUSED/CLOSED 모집 상태 동작
- `docs/DESIGN-SYSTEM.md`를 따르고 실제 서비스처럼 보이는 UI 유지
- 관련 테스트와 Frontend Phase 검증 통과
- 사용자가 보완된 V2 Frontend를 직접 확인하고 승인
