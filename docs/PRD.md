# PRD — 편의점 보관상품 판매자 검증 MVP

## 0. 문서 목적

이 문서는 편의점 앱에 보관된 1+1 / 2+1 행사 상품을 **실제로 판매하려는 사람이 존재하는지 검증하기 위한 MVP**의 제품 요구사항을 정의한다.

이번 MVP의 목적은 완성된 중고거래 플랫폼을 만드는 것이 아니다.

검증해야 할 핵심은 다음 한 문장이다.

> 편의점 앱에 남아 있는 보관상품을 돈을 받고 판매하기 위해 실제 상품 정보, 희망 가격, 증빙, 연락처를 제출하는 사람이 존재하는가?

---

# 1. 문제 정의

GS25, CU 등의 편의점에서는 1+1 / 2+1 행사 상품을 앱에 보관해 두었다가 나중에 사용할 수 있다.

그러나 보관한 상품을 직접 소비하지 못하거나 사용할 계획이 없어지는 경우가 있을 수 있다.

현재 검증하려는 문제는 다음과 같다.

> 사용하지 않을 편의점 보관상품을 가진 사람 중 일부는 상품을 그대로 소진시키기보다 일정 금액을 받고 다른 사람에게 판매하고 싶어 하는가?

여기서 중요한 것은 사용자의 단순 관심이나 설문 응답이 아니다.

실제로 판매할 의사가 있다면 사용자는 다음 행동까지 해야 한다.

- 어떤 상품을 판매할지 입력
- 유효기간 입력
- 상품 가격 입력
- 원하는 판매 가격 입력
- 실제 보관상품을 가지고 있다는 증빙 제출
- 연락 가능한 정보 제출
- 최종 판매 신청

따라서 이번 MVP는 **말로 표현한 의향이 아니라 실제 판매 신청 행동**을 측정한다.

---

# 2. 제품 목표

## Primary Goal

실제 보관상품을 가진 사용자가 판매를 위해 필요한 정보를 제출하고 **판매 신청을 완료하는지 확인한다.**

핵심 검증 행동은 다음이다.

> `판매 신청 제출 완료`

판매 신청이 완료됐다는 것은 사용자가 단순히 서비스에 관심을 보인 수준을 넘어 실제 판매 행동을 시작했다는 의미로 본다.

---

## Secondary Goal

제출된 판매 신청 중 실제 운영자 연락과 상품 처리를 거쳐 **상품 구매까지 이루어지는지 확인한다.**

즉 더 강한 검증 신호는 다음이다.

> `StoredItem.result = 구매`

이는 단순 판매 의향보다 강한 행동 증거다.

---

## Additional Signal

같은 판매자가 이후 새로운 판매 신청을 다시 제출하는지도 확인한다.

이는 다음 가능성을 판단하는 참고 신호로 사용한다.

> 편의점 보관상품 판매가 일회성 행동이 아니라 반복될 가능성이 있는가?

재판매는 이번 MVP의 필수 성공 조건은 아니다.

---

# 3. 검증 가설

## H1. 핵심 가설

> 편의점 앱에 사용하지 않을 1+1 / 2+1 보관상품을 가진 사람 중 실제로 해당 상품을 유상으로 판매하려는 사람이 존재한다.

### 검증 행동

사용자가 다음 정보를 모두 제출하여 판매 신청을 완료한다.

- 편의점
- 행사 유형
- 하나 이상의 보관상품
- 상품명
- 유효기간
- 행사 당시 가격
- 판매 희망 가격
- 판매 의향 증빙
- 연락 방식
- 연락처

단순 방문, 버튼 클릭, 판매 의향 질문에 대한 응답은 핵심 가설 검증으로 간주하지 않는다.

---

## H2. 거래 실행 가설

> 판매 신청을 완료한 사람 중 일부는 운영자가 실제로 연락했을 때 판매를 계속 진행한다.

### 강한 검증 행동

판매 신청에 포함된 하나 이상의 StoredItem이 실제로 `구매` 처리된다.

---

## H3. 반복 가능성 가설

> 한 번 판매한 사람 중 일부는 다른 보관상품도 다시 판매하려 한다.

### 검증 행동

동일한 `contact_type + contact_value`를 가진 Seller가 새로운 SaleRequest를 다시 제출한다.

이번 MVP에서는 참고 지표로만 사용한다.

---

# 4. 핵심 사용자

## 4.1 판매자

### 정의

GS25 또는 CU 앱에 1+1 / 2+1 행사로 받은 보관상품을 가지고 있으며 해당 상품을 직접 사용하지 않을 가능성이 있는 사용자.

### 사용자의 목표

> 내가 사용하지 않을 보관상품을 등록하고 실제 판매 의사를 전달한다.

### 판매자가 하지 않는 것

판매자는 이번 MVP에서 다음 기능을 사용하지 않는다.

- 회원가입
- 로그인
- 프로필 관리
- 판매 내역 조회
- 판매 상태 조회
- 신청 수정
- 신청 취소
- 구매자 탐색
- 채팅
- 결제
- 정산

판매 신청 후 필요한 후속 커뮤니케이션은 운영자가 제출된 연락처를 통해 직접 진행한다.

---

# 5. 운영자

운영자는 한 명이다.

별도의 관리자 계정이나 관리자 권한 시스템은 MVP 범위에 포함하지 않는다.

운영자의 역할은 다음과 같다.

### 1. 판매 신청 확인

접수된 SaleRequest와 포함된 StoredItem을 확인한다.

### 2. 판매 의향 증빙 확인

판매자가 제출한 스크린샷을 확인한다.

### 3. 판매자 연락

제출된 연락 방식과 연락처를 사용해 판매자에게 직접 연락한다.

최초 연락을 시작하면 SaleRequest 상태를 `연락중`으로 변경한다.

### 4. 상품별 처리

각 StoredItem을 다음 중 하나로 최종 처리한다.

- 구매
- 거절

### 5. 구매 증빙 기록

구매한 상품에는 구매 증빙을 등록한다.

### 6. 거절 이유 기록

구매하지 않은 상품에는 거절 이유를 기록한다.

### 7. 판매 신청 완료

SaleRequest에 포함된 모든 StoredItem이 `구매` 또는 `거절` 상태가 되면 해당 SaleRequest를 `처리완료`로 변경한다.

---

# 6. 핵심 사용자 플로우

## 판매자 플로우

```text
서비스 진입
↓
판매할 편의점 선택
↓
행사 유형 선택
↓
보관상품 입력
↓
필요한 경우 보관상품 추가
↓
판매 의향 증빙 스크린샷 제출
↓
연락 방법 선택
↓
연락처 입력
↓
입력 내용 확인
↓
판매 신청 제출
↓
신청 완료
```

한 SaleRequest 안에서 다음 값은 모든 StoredItem에 공통이다.

- convenience_store
- promotion_type

예:

```text
GS25
1+1

상품 A
상품 B
상품 C
```

가능

하지만 다음 구성은 불가능하다.

```text
GS25 상품
CU 상품
```

또는

```text
1+1 상품
2+1 상품
```

여러 편의점 또는 행사 유형의 상품을 판매하고 싶다면 각각 별도의 SaleRequest를 제출한다.

# 8. MVP 기능

## 8.1 판매자 — 판매 신청 생성

판매자는 새로운 SaleRequest를 생성할 수 있다.

필수 정보:

- 편의점
- 행사 유형
- 보관상품 1개 이상
- 판매 의향 증빙 스크린샷
- 연락 방식
- 연락처

---

## 8.2 편의점 선택

지원하는 값은 두 개로 제한한다.

```text
GS25
CU
```

직접 입력은 허용하지 않는다.

---

## 8.3 행사 유형 선택

지원하는 값은 두 개로 제한한다.

```text
1+1
2+1
```

직접 입력은 허용하지 않는다.

---

# 9. 보관상품 등록

한 판매 신청에는 하나 이상의 StoredItem이 필요하다.

각 보관상품에는 다음 정보를 입력한다.

- 상품명
- 유효기간
- 행사 당시 가격
- 판매 희망 가격

기프티콘 또는 앱의 보관상품 한 개를 StoredItem 한 개로 취급한다.

별도의 수량 입력은 제공하지 않는다.

같은 상품을 여러 개 가지고 있다면 각각 별도 StoredItem으로 입력한다.

---

# 10. 가격

가격 단위는 대한민국 원(KRW)만 사용한다.

저장 값은 정수다.

예:

```text
1500
2000
2500
```

다음 값은 허용하지 않는다.

```text
-1000
1.5
문자열
빈 값
```

### 행사 당시 가격

사용자가 해당 상품의 행사 당시 가격을 입력한다.

### 판매 희망 가격

사용자가 실제로 받고 싶은 금액을 입력한다.

MVP에서는 판매 희망 가격을 플랫폼이 자동으로 결정하지 않는다.

할인율 추천이나 가격 제안 기능도 제공하지 않는다.

또한 MVP에서는 판매 희망 가격이 행사 당시 가격보다 낮아야 한다는 규칙을 강제하지 않는다.

비정상적인 가격이라고 판단될 경우 운영자가 실제 구매 과정에서 거절할 수 있다.

이를 통해 판매자가 실제로 원하는 가격 데이터도 그대로 확보한다.

---

# 11. 유효기간

각 StoredItem에는 유효기간이 필요하다.

유효기간은 날짜 단위로 관리한다.

이미 유효기간이 지난 상품은 새로운 판매 신청에 등록할 수 없도록 한다.

당일이 유효기간인 상품은 등록 가능하다.

---

# 12. 판매 의향 증빙

SaleRequest에는 판매 의향 증빙 스크린샷 1장이 필수다.

목적은 단순 설문 응답이 아니라 사용자가 실제 보관상품을 가지고 있다는 최소한의 행동 증거를 확보하는 것이다.

MVP에서는 다음 기능을 제공하지 않는다.

- 이미지 자동 분석
- OCR
- 상품 정보 자동 추출
- 이미지와 StoredItem 자동 매칭
- 이미지 진위 자동 판별

운영자가 직접 확인한다.

---

# 13. 판매자 식별

회원가입을 사용하지 않는다.

판매자가 입력하는 정보는 다음 두 가지다.

### contact_type

```text
phone
kakao
```

### contact_value

선택한 방식의 실제 연락처 값.

판매자 식별 기준은 다음과 같다.

```text
contact_type + contact_value
```

두 값의 조합이 기존 Seller와 동일하다면 기존 Seller를 사용한다.

동일한 Seller가 없다면 새로운 Seller를 생성한다.

예:

```text
phone + 01012345678
```

이 조합이 같으면 같은 Seller다.

전화번호와 카카오 연락처가 같은 사람인지 별도로 추론하지 않는다.

---

# 14. 판매 신청 상태

SaleRequest 상태는 세 가지다.

```text
접수됨
연락중
처리완료
```

## 접수됨

판매자가 판매 신청을 정상적으로 제출한 상태.

새 SaleRequest의 초기 상태다.

## 연락중

운영자가 판매자에게 최초 연락을 시작한 상태.

## 처리완료

판매 신청에 포함된 모든 StoredItem이 최종적으로 다음 중 하나가 된 상태.

```text
구매
거절
```

미처리 StoredItem이 하나라도 존재하면 처리완료가 될 수 없다.

---

# 15. 보관상품 처리 결과

StoredItem의 result는 세 가지다.

```text
미처리
구매
거절
```

새 StoredItem의 초기 상태는 `미처리`다.

---

## 미처리

```text
result = 미처리
rejection_reason = 없음
purchase_evidence = 없음
```

---

## 구매

```text
result = 구매
purchase_evidence = 필수
rejection_reason = 없음
```

구매 증빙 없이 구매 상태로 최종 처리할 수 없다.

---

## 거절

```text
result = 거절
rejection_reason = 필수
purchase_evidence = 없음
```

거절 이유 없이 거절 상태로 최종 처리할 수 없다.

---

# 16. 처리 결과 불변성

한 번 StoredItem이 다음 상태가 되면

```text
구매
또는
거절
```

MVP에서는 다른 상태로 다시 변경할 수 없다.

예:

```text
구매 → 거절
거절 → 구매
구매 → 미처리
거절 → 미처리
```

모두 지원하지 않는다.

잘못 처리했을 때 결과를 되돌리는 별도 기능도 MVP에서는 만들지 않는다.

이는 운영자 한 명이 진행하는 소규모 검증 단계라는 점을 전제로 한다.

---

# 17. 판매 신청 자동 완료 규칙

SaleRequest에 포함된 모든 StoredItem이 최종 처리되면 SaleRequest는 `처리완료`가 된다.

예:

```text
상품 A → 구매
상품 B → 구매
상품 C → 거절

=> SaleRequest 처리완료
```

반면:

```text
상품 A → 구매
상품 B → 거절
상품 C → 미처리

=> SaleRequest 연락중
```

SaleRequest의 완료 여부는 개별 StoredItem 상태를 기준으로 판단한다.

---

# 18. 판매 신청 완료 후 사용자 경험

판매 신청이 정상적으로 완료되면 판매자에게 다음 사실만 명확히 전달한다.

- 신청이 정상적으로 접수되었음
- 운영자가 내용을 확인함
- 필요한 경우 제출한 연락처로 연락함

판매자는 사이트에서 신청 상태를 다시 조회하지 않는다.

따라서 다음 기능은 만들지 않는다.

- 신청 번호 조회
- 판매 내역 페이지

# 21. 성공 기준

이번 PRD에서는 임의의 방문자 수나 전환율을 제품 요구사항으로 고정하지 않는다.

유입 채널과 실제 모집 규모가 결정되기 전에 예를 들어 `전환율 10% 이상` 같은 수치를 정하면 검증 목적과 관계없는 숫자가 될 가능성이 높기 때문이다.

대신 검증 신호의 강도를 다음과 같이 정의한다.

## Level 0 — 관심

```text
서비스 방문
판매 시작 버튼 클릭
```

핵심 가설의 증거로 사용하지 않는다.

---

## Level 1 — 핵심 검증

```text
유효한 SaleRequest 제출
```

실제 상품 정보, 가격, 증빙, 연락처까지 입력한 판매자가 존재한다.

**핵심 판매자 가설을 지지하는 최초의 행동 증거다.**

---

## Level 2 — 강한 검증

```text
StoredItem 실제 구매
```

신청자가 운영자의 실제 연락에 응하고 거래까지 진행한다.

Level 1보다 훨씬 강한 판매 의향 증거다.

---

## Level 3 — 반복 신호

```text
동일 Seller가 새로운 SaleRequest 제출
```

판매 행동이 일회성에 그치지 않을 가능성을 보여준다.

이번 MVP의 필수 성공 조건은 아니다.

제품 DB에 이미 존재하는 데이터와 배포 플랫폼에서 제공하는 최소 방문 데이터를 우선 활용한다.

# 23. 핵심 비즈니스 규칙 요약

```text
1. Seller는 contact_type + contact_value 조합으로 식별한다.

2. 하나의 SaleRequest에는 하나의 Seller만 존재한다.

3. 하나의 SaleRequest에는 하나의 편의점만 존재한다.

4. 하나의 SaleRequest에는 하나의 행사 유형만 존재한다.

5. SaleRequest에는 최소 1개의 StoredItem이 필요하다.

6. StoredItem 하나는 실제 보관상품 1개를 의미한다.

7. 별도의 quantity는 사용하지 않는다.

8. 새 SaleRequest의 상태는 접수됨이다.

9. 새 StoredItem의 결과는 미처리다.

10. 미처리 상품에는 거절 이유와 구매 증빙이 없어야 한다.

11. 구매 상품에는 구매 증빙이 반드시 필요하다.

12. 구매 상품에는 거절 이유가 없어야 한다.

13. 거절 상품에는 거절 이유가 반드시 필요하다.

14. 거절 상품에는 구매 증빙이 없어야 한다.

15. 구매 또는 거절로 확정된 상품은 다시 변경하지 않는다.

16. 모든 StoredItem이 구매 또는 거절되면 SaleRequest는 처리완료가 된다.

17. 미처리 StoredItem이 하나라도 있으면 SaleRequest는 처리완료가 될 수 없다.

18. 판매자는 제출 이후 사이트에서 신청을 수정하거나 취소하지 않는다.

19. 운영자는 한 명이다.

20. MVP에서는 실제 판매 가능성을 검증하는 데 직접 필요하지 않은 기능을 추가하지 않는다.
```

# 24. 제품 원칙

이번 MVP의 의사결정 우선순위는 다음과 같다.

### 1. 실제 행동을 측정한다

설문 응답보다 실제 판매 신청을 우선한다.

### 2. 입력 마찰을 최소화한다

검증에 필요하지 않은 정보는 요구하지 않는다.

### 3. 데이터 신뢰성은 유지한다

사용자 경험을 단순화하더라도 판매자, 신청, 상품 간 데이터 관계와 핵심 상태 규칙은 깨뜨리지 않는다.

### 4. 운영자가 직접 할 수 있는 일은 자동화하지 않는다

초기 소규모 검증에서 사람이 처리해도 충분한 작업을 위한 시스템을 만들지 않는다.

### 5. 미래 기능을 미리 만들지 않는다

향후 거래 플랫폼으로 발전할 가능성이 있더라도 현재 검증에 필요하지 않은 구조나 기능은 추가하지 않는다.

### 6. 모바일을 우선한다

판매자는 편의점 앱에 보관된 상품을 확인하면서 서비스를 사용할 가능성이 높으므로 판매 등록 경험은 모바일을 최우선으로 설계한다.

# 25. PRD 완료 조건

다음 질문에 명확하게 답할 수 있으면 이 PRD는 역할을 다한 것으로 본다.

> 누가 사용하는가?

편의점 앱의 보관상품을 실제로 판매하고 싶은 사람.

> 어떤 행동을 검증하는가?

실제 상품, 가격, 증빙, 연락처를 포함한 판매 신청 제출.

> 더 강한 검증은 무엇인가?

등록된 상품이 운영자와의 연락 후 실제 구매되는 것.

> 제품은 어디까지 책임지는가?

판매 신청 접수와 운영자의 실제 처리 기록까지.

> 제품이 책임지지 않는 것은 무엇인가?

회원 시스템, 구매자 시장, 결제, 정산, 채팅, 자동화 등 실제 거래 플랫폼 확장 기능.
